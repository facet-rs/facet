# zlib + libpng, as a single-file vix package

Design fiction, written to pressure the literal/template design
(`r[lang.literal.*]`, `r[lang.template.*]`) and the frontmatter manifest
(`r[vixen.package.frontmatter]`) against a build that has all the awkward
parts: pinned foreign source, per-file compilation, a generated config
header, a generated program, and a link step consuming earlier outputs.

Nothing here runs. The value is the list below — writing it surfaced four
things the spec does not answer, and two places where writing real code
disagreed with what the spec says.

## What it validates

- **Frontmatter carries a real manifest.** Two `@fetch` inputs with upstream
  digests, one command. The whole package is one file.
- **A template is a function.** `Template<Image>` is applied as
  `mandelbrot()(Image { … })`; the struct describing the picture *is* the
  struct filling the source. No fill-API was needed.
- **The `{}` collision is real and the design survives it.** The C program is
  dense with braces and none of them are holes — which is the case that forced
  hole delimiters to be per-capability data rather than one global choice.
- **No control flow was missed.** Fifteen translation units are `map` over a
  list; nothing wanted a loop inside a literal.
- **Block strings hold foreign source verbatim.** Indentation strips to the
  closing fence; the emitted C is at column zero.

## Gaps — the point of the exercise

**GAP 1 — a hole that expands to many argv elements.** `ar rcs {lib} {objects}`
needs fifteen objects to become fifteen argv elements from one hole. Today a
hole is one value; the spec never says a `[Path]` hole spreads. Without it a C
library cannot be archived and a linker cannot be given its inputs, so this is
not a nicety — it is the first blocker. It is presumably where the parked
`Arg::{Str, Path, Interpolation}` design lands, and it needs a rule saying
whether spreading is implicit for a list-typed hole or explicitly spelled.

**GAP 2 — how does code reach a declared input? — RESOLVED, by retraction.**
The sketch declared `input { zlib @fetch{…} }` and then wanted that input back
as a **Tree**, writing `input("zlib")` — a surface nothing in the spec
provided. The gap was real and its answer was that the question was wrong:
there is no declared input. `r[vixen.package.inputs-are-provider-pins]` has
been struck, the manifest declares surface and not provenance, and code
fetches what it needs as an ordinary demand whenever it needs it. The two
things this gap noticed were "wearing one section" — source inputs and
capability-provider pins — are indeed different questions; the first is
discharged by code, and the second still has no home.

The `manifest` block below is therefore stale in exactly this respect and is
left as written, because the sketch's value is the record of what writing it
surfaced.

**GAP 3 — output binding vs. names that matter.** `{let obj}` allocates a
plan-determined path, which is right for object files (nobody cares what a
`.o` is called, and a stable name is a cache-miss hazard). It is *not* right
when the name is load-bearing: `-lz` looks for `libz.a`. The sketch works
around this by returning a `Built { tree, path }` and splicing `{png.path}`
rather than a filename — which is arguably better discipline, but it means a
build that must produce a *specifically named* artifact has no spelling. An
`Output<Path>` role with a caller-chosen name needs a rule, and it has to stay
plan-determined to keep `r[lang.template.command-holes]`'s identity promise.

**GAP 4 — Tree construction.** `Tree::empty()`, `Tree::file(path, bytes)`, and
`.merge(other)` are all invented here. Projection (`tree / path`) exists;
building a tree from generated bytes does not. File generation is impossible
without it, and it is the one gap that blocks the stated goal most directly —
`libpng_config` and the generated `mandelbrot.c` both need it.

## Where the sketch disagreed with the spec

**A call inside a hole.** The first draft wrote `-I{input("zlib")}/zlib-1.3.1`.
Templates splice *bare names*, so that is not admissible; the sketch now binds
`zlib_headers` first. The restriction is defensible (a hole stays trivially
readable) but it is worth stating in `r[lang.template.holes]` rather than
leaving it to be discovered, since the natural way to write this hits it
immediately.

**Where an output binding lives.** `r[lang.template.command-holes]` says
`{let obj}` binds *in the enclosing scope*. Writing the code, the hand reaches
for `built.obj` — the path is intuitively a property of the command that
produced it, not a name floating in the function. The sketch follows the spec
(`{let bin}` then bare `bin`), and it reads slightly oddly next to
`linked.tree` on the previous line: two results of one command, reached two
different ways. Worth revisiting; the outcome-field model was rejected earlier
for needing a per-call-site record type, and that cost may be worth paying.

## Not attempted

macOS/Linux divergence beyond what `cc` absorbs; shared libraries; `libpng`'s
ARM/Intel SIMD paths (the prebuilt config disables them); installing headers.
The point was to reach a `.png` on disk, not to replace `configure`.
